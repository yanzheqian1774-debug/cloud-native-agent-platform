# Exact context admission registry and explicit renewal (G1)

Scope: keep the existing ContextApproval HTTP body and original context/decision tables. Register only actual initialized admission owners from bootstrap. Select by the entire immutable stored configuration plus planning/understanding phase; missing or ambiguous owners fail closed. Read, approve and revoke still call the selected original owner. No browser-selected profile, arbitrary configuration factory, service-to-human adaptation or invocation dispatch is introduced.

The implementation gate is G1: internal composition and an optional private renewal plan behind the existing authenticated API. No public CRD, lifecycle, tenant, authentication or storage schema changes. Original admin, no-self-approval, current account/generation and eight-hour SQL constraints remain.

Explicit renewal is default off. A root-prepared private plan must pin issuer, subject, scope, original request digest/full configuration, prior decision, exact target generation/recovery epoch, command key and requested expiry, global authorization cutoff and authorization evidence digest. A still-valid prior preserves its expiry. An expired prior requires a separately explicit bounded-renewal entry; never extend the global deadline. No automatic enumeration, approval or model call. Service contexts are excluded.

Inside the original approve transaction, after account/admin/context locks, verify the plan and prior immutable request/decision and revocation before any append, including replay. Original first approval hooks remain unchanged. An explicitly verified renewal must not run PlanningCallAdmission's legacy 8-to-20 allowance-creation hook: this path only appends a new context decision, creates no allowance, and preserves original configuration/budget. Exact execution/model/source permissions remain checked on future dispatch by their current owners. Old UNKNOWN, active and settled invocations are never resumed, altered or replayed by this operation. Renewing a context is not authority to replay an invocation.

Compatibility: existing API without a plan delegates the exact owner and retains its original approval behavior. Root approval/receipt tooling uses the same POST and records original and resulting decision identities; no new public proof fields. This patch does not install a plan or execute that tooling. Configuration slots not currently initialized cannot be invented from rows.

Validation: selection across actual configs/phases; unknown, ambiguous, cross-scope and service rows rejected; legacy canonical body unchanged; valid lease unchanged, expired explicit lease bounded; revoked prior/replay denied; planning renewal never creates an allowance; old approval hook retained; old invocation data untouched. Pure/controlled owner contract tests first; no actual DB, provider or install. Independent review required before root integration.


## Reviewed tightening
Renewal additionally reads the original allowance through provider_budget_allowance.require_context on the same transaction. The entry pins allowance identity and authorization digest; a request carrying its own allowance must match those original fields. The plan global cutoff must equal the immutable allowance's verified expiresAt (root digest, scope, validity and bounded original configuration are checked by that owner). This adds no allowance and does not change a smaller original context cap. The subject's current local-account principal/scope/status/revision are all checked, and the subject must be human. Missing/unregistered configurations are explicit blockers, never guessed from rows.

Private configuration is opt-in with CONTEXT_CALL_READMISSION_PLAN and CONTEXT_CALL_READMISSION_PLAN_SHA256. The file must be absolute, a non-symlink regular file owned by the process user with mode0600, <=1MiB, exact SHA, strict schema, unique JSON keys/context IDs/command keys. Browser requests cannot supply the plan. The runtime must be composed with the actual initialized model-specific owners; changing these private fields is an explicit deployment, not hot loading.

The same API returns the appended existing decision row, whose immutable record includes a typed context-readmission-receipt.v1 (plan digest, original evidence digest, lease mode, prior decision ID). This is an authorization fact, not a model call, a human-review claim, or permission to replay an old call. Replay rechecks the current account/admin/generation, original allowance validity and revocation before observing the same receipt. A later decision or expired renewed lease requires another reviewed plan rather than silently extending or reusing the old one.

## Root operator sequence (not executed)
1. Freeze exact installed source and initialized owner inventory. Export only current immutable request, prior decision/record digest, subject/account/scope, original allowance identity/authorization/cutoff and current revocation observations. Match each complete configuration to one initialized owner. List unmatched contexts separately; do not create an owner from exported data.
2. Prepare a private plan for the target generation/epoch and a real independent browser issuer. Preserve live expiry exactly; for expired entries pin an explicitly authorized new lease <=8h and <=the same immutable allowance cutoff. Choose one stable key per exact entry. Preserve all old invocation IDs/states, including UNKNOWN. Service contexts remain on their service owner.
3. After formal generation activation, reload runtime owners, log in through the existing formal browser service, and GET the original context through the same API. POST only the exact plan's ContextApproval once. Read back the returned decision and verify context/request/config/subject/predecessor/currentgeneration/expiry/receipt; retain the raw receipt. A lost response uses GET/that same key only, never a new lease or model call. Conflicts/revocation/unknown owner stop that entry.
4. Verify old requests/invocations/budget reservations and settlements unchanged, only explicit decision/audit appends. Verify old conversation/resource/result READ separately; ordinary current READ is not task-delegation identity-continuity proof. No service start or invocation is part of this operation.

Validation boundary: dedicated53429 random accounts databases; no actual environment. Current generation test uses the real repository activation and fresh sessions/readers, not a full production host/controller transition. Registry tests exercise exact-selection contracts with controlled owners; existing composition tests are a separate compatibility check. Actual initialized inventory and installed read-back remain root gates.
