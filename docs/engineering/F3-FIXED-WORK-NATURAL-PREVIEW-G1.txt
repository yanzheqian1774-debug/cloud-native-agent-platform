G1 successor: natural-language fixed-work configuration preview via original authoring owner
Status: implementation design, default off; not completed automation or model understanding.

Prototype source: V6.9-F3 frozen interaction HTML, final put4('team-routines','团队固定工作 · 自然语言管理') and put4('routine-nl',...). It presents a natural-language instruction, before/after table, expandable explicit corrections, then original configuration confirmation. Its parseNL6 is a local exact-pattern demonstration; the prototype itself distinguishes this from real scheduling. Its hardcoded capabilities/people/supplier defaults must NOT become platform facts.

Current actual owners:
- FixedWorkAuthoringOwner: exact TEAM READ + authoring READ policy; SAVE additionally TEAM REVISE + SAVE policy, immutable revision/CAS/idempotent receipt.
- AuthoringPolicy and SaveDraft/TriggerDraft: exact revision/digest, timezone, time, WEEKDAY/DAILY or literal event description. No capacity/source/worker fields currently exist in the configuration record.
- Existing FixedWorkPlanPreview renders literal text and explicit fields; it does not interpret natural-language schedule. ServicePlanningRuntime only models its independently bound confirmed Problem/Criteria, not the literal configuration instruction.

Smallest truthful implementation:
1. Add pure conservative parser of explicit supported expressions to the existing configuration domain: Arabic HH:mm or N点/半 + explicitly 每天/工作日, optional explicit Shanghai timezone. No unspecified default time; ambiguous multiple times, conflicting frequencies, unsupported week/month/hour/minute recurrence -> issue requiring correction. Event input may preserve explicitly supplied event text, but cannot claim an event adapter exists.
2. A default-off POST PREVIEW_FIXED_WORK_INSTRUCTION under exact team/revision calls the original READ authoring policy and exact TEAM READ. For existing work it reads the immutable current work via original owner, verifies expected revision/digest; for new work it reads same exact team/policy with no fictitious prior object. Input text retained intact. Output candidate is STRUCTURE_ONLY with original field values, proposed values, per-field derivation (EXPLICIT_TEXT/UNCHANGED/NEEDS_CONFIRMATION), issues and actual work baseline. No model claim, grants, configuration save or trigger.
3. Preserve original authoring confirmation owner and payload. Client explicitly confirms the concrete parsed/corrected fields using SaveDraft. Existing expectedVersion/predecessorRevisionId catches races. Original immutable command key/body and UNKNOWN-save recovery remain unchanged. Preview is advisory and grants no CREATE/REVISE or authority; malicious clients already cannot bypass existing SAVE gates.
4. Natural-language-first F3 UI shows one instruction input and preview/difference; explicit schedule fields move into expandable corrections. Existing saved version, pending command, no-response recovery, READ-only controls, session epoch fences and internal return context survive. Show actual missing capability/source/service-binding as pending system support, not invented resources or an instruction for users to approve infrastructure.
5. The schedule parser is not business-goal/model understanding. Original-user conversation understanding for new Problem/Criteria remains a separate pending bridge. It cannot reuse ConversationJourney unchanged: applyUnderstanding transitions to CREATE then PLAN/execution automatically, contrary to preview-only. That follow-up must persist exact work/owner/instruction binding and explicitly stop at preview before execution owners. The old private message max2048 vs configuration max4000 must be handled explicitly without truncation.
