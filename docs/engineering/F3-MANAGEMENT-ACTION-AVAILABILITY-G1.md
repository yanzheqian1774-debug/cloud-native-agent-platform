# F3 management action availability — G1 proposal

Status: implemented isolated candidate; root approved G1 and compatibility refinement. No actual platform writes. Isolated tree based on 6afdad plus the frozen team-return patch. Existing F3 pages/layout and formal owner operations remain.

## Confirmed mismatch

TeamsPage exposes creation and current-head modification without checking TEAM CREATE/REVISE. DigitalEmployeesPage exposes creation unconditionally and modification when authoring.head.status is AVAILABLE. workbench_employee_relations computes AVAILABLE from EMPLOYEE READ, not mutation grants. Professional EmployeeSuccessorPanel/EmployeeLifecycleActions also need the same restriction; guarding only business-mode entry is insufficient. Neither mismatch grants backend authority.

## Minimal read interfaces

1. GET /teams/capabilities, observes only the currently authenticated subject; returns current scope/subject/generation/readAt and action availability for CREATE on team:collection. GET /employees/capabilities likewise observes only the current authenticated subject and projects EMPLOYEE CREATE employee:collection. These collection endpoints do not enumerate hidden identities or grant permission. Direct creation URLs must await this projection; no projection means no submit controls.
2. Existing READ_TEAM_REVISION exact READ adds optional maintenanceActions bound to current subject, scope, teamId, revisionId, digest, aggregateVersion and headRevisionId. REVISE tests TEAM REVISE team:<teamId>:aggregate. effective availability also requires viewed revision=head. CREATE is not inferred from REVISE.
3. Existing employee authoring read adds maintenanceActions for each exact readable parent/head definition (unreadable head remains unavailable), bound to subject, scope, employee identity/revision/digest/aggregateVersion. Actual owner actions are CREATE on employee:collection (including successor), VALIDATE/APPROVE/PUBLISH on employee:<id>:aggregate. Do NOT invent EMPLOYEE REVISE. Lifecycle eligibility follows the actual per-revision DRAFT/VALIDATED/APPROVED owner rules (no invented current-head restriction). Successor eligibility follows the existing unused-predecessor query, not head identity; business entry still selects its existing current head. permission and lifecycle status are separate facts. No published resource implies a mutation grant.

Each projection reports authorized boolean and lifecycleEligible separately, with executionStarted=false/authorityGranted=false. Unknown/unavailable is not denied: authority backend errors yield unavailable and UI offers read-only refresh, never permissive fallback. Metadata uses current owner transaction and authority generation/recovery epoch. No persistent schema, new grants, policy/generation edits or model calls.

## Shared implementation boundary

Add a read-only method to AuthorizedOwnerAuthority (or equivalent narrowly factored helper) that validates registered exact grants and invokes adapter.authorization.has_current_grants with current context, clock, generation, recovery epoch, same connection, configure_transaction=False, require_available=True. It must not call _decision or populate mutation decisions. Use the same existing grant builders as commands to avoid target drift. Existing POST require/canonical state/member validation stays authoritative and rechecks at submit. A positive UI observation is not a capability token or guarantee all edited member inputs will pass owner validation.

## UI semantics

Missing projection defaults to read-only; do not silently accept old fixtures without capability facts. Bind responses to initiating principal/scope/exact version and reject late responses. Session invalidation and selected-object changes clear availability. Recheck on focus/explicit refresh and immediately before new submission. Hide unavailable mutation controls rather than enable then fail; display concise readonly explanation. Frozen UNKNOWN team/successor/lifecycle commands retain existing original read recovery; legacy initial employee creation retains its authorized exact commandId/body idempotent owner replay (repository checks payload digest and returns original revision before creating anything); revocation must not delete saved drafts or convert UNKNOWN into permission to resubmit. Never issue a write on capability GET, refresh or mount.

Both employee business and professional paths, direct mode=create / employeeEdit URLs, team new=1 and existing edit restoration must use this same projection. Team owner-candidate GET currently requires CREATE even during REVISE; preserve this contract: exact team projection includes SELECT_OWNER from that existing CREATE grant, so a REVISE-only editor keeps the original owner and sees an unavailable-candidate explanation. No broadened read rule. If product requires REVISE-only reassignment, report that separate exact owner API issue rather than pretending capability projection fixes it.

Compatibility refinement approved by root: collection observation must work for CREATE-only subjects without LIST. Generic empty-grant owner calls remain rejected. Only the two fixed capability operations, with no path/query/payload, use fixed CREATE probes in the generation-pinned owner transaction and a separate require_current_context read using the existing linearized context reader and _current_credential validator (has_current_grants behavior/signature unchanged).
