# ADR-0001: Use Kubernetes as the Agent Platform Control Plane

- Status: Accepted
- Date: 2026-08-10
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

The platform is intended to manage multiple AI agents as long-running,
dynamically scheduled, independently scalable workloads.

Agents may have different:

- models and model providers;
- CPU, memory, and GPU requirements;
- runtime configurations;
- tools, skills, and MCP capabilities;
- lifecycle and health requirements;
- scaling and availability requirements.

The platform therefore needs more than an API for invoking language models.
It needs a control plane capable of describing desired state, scheduling
workloads, managing lifecycle, recovering from failures, isolating resources,
and providing a foundation for observability and policy enforcement.

Building these capabilities directly into a custom agent scheduler would
duplicate many capabilities already provided by Kubernetes.

## Decision

Kubernetes will be used as the infrastructure control plane for the
Cloud Native Agent Platform.

Kubernetes will be responsible for infrastructure-level concerns including:

- workload scheduling;
- resource allocation;
- container lifecycle;
- health checking and restart;
- service discovery;
- configuration and secret distribution;
- horizontal scaling;
- namespace isolation;
- infrastructure observability integration.

Agent-specific concepts will be introduced on top of Kubernetes rather than
implemented as a replacement for Kubernetes.

The initial architecture separates two logical planes:

### Control Plane

The control plane describes and reconciles the desired state of agents.

It will contain components such as:

- Agent Custom Resources;
- Agent Operator;
- lifecycle reconciliation;
- scheduling and placement policies;
- platform policy;
- infrastructure observability.

### Agent/Data Plane

The agent/data plane executes actual AI workloads.

It will contain components such as:

- Agent Runtime;
- workflow execution;
- tools and skills;
- MCP integrations;
- memory;
- model-provider clients.

Kubernetes manages the infrastructure lifecycle of these workloads, while the
Agent Platform manages agent semantics and execution behavior.

## Alternatives Considered

### Custom Agent Scheduler

Build a dedicated scheduler and lifecycle manager specifically for AI agents.

Rejected because it would require the project to independently implement
scheduling, failure recovery, service discovery, resource isolation, rollout,
configuration management, and other infrastructure capabilities already
available in Kubernetes.

### Docker Compose

Docker Compose is useful for local development but does not provide the
declarative control-plane and reconciliation capabilities required by the
target platform.

It may still be used for lightweight local development scenarios.

### Direct Virtual Machine Deployment

Deploying agent processes directly onto virtual machines provides flexibility
but makes lifecycle management, scheduling, scaling, isolation, and
reproducibility significantly more difficult.

### Managed Agent Platforms

Managed agent services may reduce operational complexity but can introduce
provider coupling and make it harder to experiment with the platform-level
control-plane concepts this project is intended to validate.

They may later be integrated as external execution backends.

## Consequences

### Positive

- Reuses a mature declarative infrastructure control plane.
- Provides scheduling and resource isolation primitives.
- Supports CPU and GPU workloads.
- Provides self-healing and lifecycle management.
- Enables future multi-node and cloud deployment.
- Integrates with the broader cloud-native ecosystem.
- Creates a natural foundation for Agent CRDs and Operators.

### Negative

- Introduces Kubernetes operational complexity.
- Raises the learning curve for contributors.
- Local development requires a Kubernetes environment.
- Kubernetes abstractions must not leak unnecessarily into agent business logic.
- Kubernetes alone does not solve agent orchestration, memory, reasoning, or workflow semantics.

## Architectural Boundary

Kubernetes is responsible for:

    "Where and under what infrastructure conditions should the agent run?"

The Agent Platform is responsible for:

    "What should the agent do, how should agents collaborate,
     and how should the task be executed?"

This boundary is fundamental to subsequent architecture decisions.
