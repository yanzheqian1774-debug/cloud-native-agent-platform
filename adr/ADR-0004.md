# ADR-0004: Introduce a Pluggable Agent Runtime Architecture

- Status: Accepted
- Date: 2026-08-10
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

ADR-0001 establishes Kubernetes as the infrastructure control plane.

ADR-0002 defines Agent as a declarative enterprise resource.

ADR-0003 defines the Operator and reconciliation pattern for Agent
infrastructure lifecycle.

The platform must now define how an Agent is actually executed.

Different Agent runtimes and frameworks may provide different capabilities
and execution semantics.

Examples include:

- the platform-native runtime;
- Hermes;
- LangGraph;
- kagent;
- existing enterprise Agent platforms;
- external Agent services.

The Enterprise Agent OS must not become tightly coupled to a single Agent
framework.

A stable abstraction is therefore required between the Agent control plane and
runtime-specific implementations.

## Decision

The platform will introduce a pluggable Agent Runtime architecture.

Each Agent declares a runtime class.

The Agent Operator resolves the runtime class and delegates runtime-specific
infrastructure operations through a Runtime Adapter contract.

Conceptually:

    Agent
      |
      | runtimeClass
      v
    RuntimeClass
      |
      v
    Runtime Resolver
      |
      v
    Runtime Adapter
      |
      +----------------+----------------+----------------+
      |                |                |                |
      v                v                v                v
    Native           Hermes          LangGraph        External
    Runtime          Runtime         Runtime          Runtime

The core Agent Operator must not embed framework-specific lifecycle logic.

## Runtime Responsibilities

An Agent Runtime is responsible for executing Agent behavior.

Depending on the runtime implementation, responsibilities may include:

- loading Agent role or profile configuration;
- model interaction;
- tool execution;
- MCP interaction;
- skill execution;
- session handling;
- runtime memory;
- task execution;
- framework-specific reasoning and orchestration.

These responsibilities remain outside the Agent Operator.

## RuntimeClass

A RuntimeClass represents a reusable description of how a class of Agent
runtime is resolved and managed.

The initial conceptual structure may include:

    spec:
      mode:

      adapter:
        type:

      configurationRef:

      workload:
        image:

      endpoint:
        configRef:

      capabilities:

The exact schema will be defined during implementation.

## Runtime Modes

The platform should support multiple runtime deployment models.

### Managed Runtime

The Enterprise Agent OS creates and manages the runtime infrastructure.

Example:

    Agent
      |
      v
    Agent Operator
      |
      v
    Native Runtime Adapter
      |
      v
    Deployment / Pod

The runtime lifecycle is fully managed by the platform.

### Remote Runtime

The runtime already exists in the enterprise environment.

Example:

    Agent
      |
      v
    Hermes Runtime Adapter
      |
      v
    Existing Hermes Gateway

The Agent OS manages the logical Agent registration and observed availability
but may not own the underlying runtime process.

### External Runtime

The runtime is provided by an external platform or service.

Example:

    Agent
      |
      v
    External Runtime Adapter
      |
      v
    External Agent Service API

The Enterprise Agent OS treats the external runtime as a federated execution
backend.

## Runtime Adapter Contract

The Runtime Adapter hides runtime-specific lifecycle implementation from the
core Agent Operator.

The initial conceptual interface includes:

    resolve(agent)

    provision(agent)

    update(agent)

    delete(agent)

    observe(agent)

The interface may later evolve to include capabilities such as:

    scale(agent)

    health(agent)

    capabilities(agent)

The initial implementation should remain intentionally small.

## Resolve

`resolve` determines whether the runtime configuration required by the Agent
can be located and used.

Examples include:

- RuntimeClass exists;
- required runtime configuration exists;
- endpoint configuration is available;
- runtime adapter implementation is registered.

## Provision

`provision` ensures the infrastructure or logical registration required to
make the Agent available.

For managed runtimes this may create Kubernetes resources.

For remote or external runtimes this may create logical registration or
binding state.

## Update

`update` converges runtime-specific infrastructure or registration toward the
new declared Agent state.

The implementation must be idempotent.

## Delete

`delete` removes runtime-specific infrastructure or logical registration owned
by the Agent OS.

The adapter must respect ownership boundaries.

For remote or external runtimes, deleting an Agent must not automatically
destroy external infrastructure unless ownership has been explicitly
established.

## Observe

`observe` reports infrastructure-level runtime state back to the Agent
Operator.

Conceptual observations may include:

    ready:
    readyReplicas:
    endpoint:
    runtimeVersion:
    message:

Runtime observation must not include high-frequency Agent execution data.

## Runtime Capabilities

Different runtimes may support different optional features.

Examples include:

- multi-Agent delegation;
- long-running sessions;
- persistent memory;
- tool execution;
- MCP;
- skill systems;
- code execution;
- browser execution.

Runtime capabilities should be discoverable through a structured capability
model.

Higher-level platform components may use capability information when deciding
whether a runtime is suitable for a workload.

The capability model must not force every runtime to implement identical
internal behavior.

## Framework Independence

The Agent OS must not assume that every runtime uses the same:

- prompt format;
- memory model;
- workflow engine;
- tool interface;
- session model;
- state representation;
- reasoning strategy.

The common contract is focused on lifecycle, availability, addressing, and
capability discovery.

Framework-specific execution semantics remain inside the runtime.

## Configuration Boundary

Runtime-specific configuration should not be embedded directly into the core
Agent schema whenever avoidable.

Instead:

    Agent
      |
      v
    RuntimeClass
      |
      v
    Runtime-specific configuration reference

This reduces coupling between the Agent API and runtime implementation details.

## Security Boundary

Runtime adapters operate across an important trust boundary.

The platform must eventually support:

- explicit runtime identity;
- scoped credentials;
- endpoint authentication;
- TLS;
- runtime authorization;
- audit logging;
- network policy.

External and remote runtimes must not automatically inherit broad Kubernetes
or enterprise permissions.

## Ownership Boundary

The platform must distinguish between resources it owns and resources it only
references.

For a managed runtime:

    Agent OS owns runtime infrastructure.

For a remote runtime:

    Agent OS may only own Agent registration or binding state.

For an external runtime:

    Agent OS may own no runtime infrastructure.

This distinction must be preserved during deletion and reconciliation.

## Alternatives Considered

### Build and Support Only a Native Runtime

Rejected because it would make the Enterprise Agent OS another vertically
integrated Agent framework and limit interoperability with existing enterprise
Agent investments.

A native runtime will still be implemented as the reference runtime.

### Embed Framework Logic in the Operator

Rejected because the core Operator would accumulate framework-specific logic
and become difficult to maintain.

### Require All Runtimes to Implement One Execution Protocol Internally

Rejected because existing Agent frameworks use different execution models.

The common abstraction should focus on the minimum control-plane contract
rather than forcing identical internal semantics.

### Treat Every External Runtime as a Generic HTTP Endpoint

Rejected as the only abstraction because lifecycle, capability discovery,
health, identity, and ownership semantics differ between runtime types.

Adapters provide a more explicit integration contract.

## Consequences

### Positive

- Preserves runtime independence.
- Allows the platform to integrate existing Agent frameworks.
- Reduces framework-specific logic in the core Operator.
- Enables runtime federation.
- Supports gradual migration from external runtimes to platform-managed
  runtimes.
- Allows a native runtime without making it mandatory.
- Creates a foundation for enterprise Agent workforce federation.

### Negative

- Introduces adapter complexity.
- Runtime capability differences must be handled explicitly.
- Compatibility testing becomes important.
- Remote and external runtime failures may be harder to diagnose.
- Lifecycle ownership semantics require careful design.

## Architectural Boundary

The Enterprise Agent OS is responsible for:

    "Which Agent should exist, which runtime class should execute it,
     and whether that runtime is available and properly bound?"

The Agent Runtime is responsible for:

    "How does this Agent actually execute its reasoning,
     model interactions, tools, memory, and framework-specific behavior?"

## Strategic Consequence

The Enterprise Agent OS is intentionally designed as an open control plane.

A high-quality external Agent runtime is not considered a threat to the
platform architecture.

Instead, external runtimes expand the digital workforce that the platform can
organize, govern, operate, and observe.
