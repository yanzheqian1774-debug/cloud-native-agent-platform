# ADR-0003: Use the Operator and Reconciliation Pattern for Agent Lifecycle

- Status: Accepted
- Date: 2026-08-10
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

ADR-0001 establishes Kubernetes as the infrastructure control plane.

ADR-0002 defines Agent as a declarative enterprise resource.

The platform therefore requires a controller responsible for continuously
converging the infrastructure state of an Agent toward the desired state
declared in the Agent resource.

The controller must manage infrastructure lifecycle without becoming
responsible for Agent reasoning, workflow orchestration, or business logic.

A clear separation is required between:

- infrastructure reconciliation;
- Agent execution;
- workflow orchestration;
- enterprise governance.

## Decision

The platform will use the Kubernetes Operator and reconciliation pattern to
manage Agent infrastructure lifecycle.

The Agent Operator watches Agent resources and related dependencies,
calculates the difference between desired and observed infrastructure state,
performs the required Kubernetes operations, and reports relevant observed
state through the Agent status subresource.

Conceptually:

    Agent.spec
        |
        v
    Desired State
        |
        v
    Agent Operator
        |
        | Reconcile
        v
    Runtime Adapter
        |
        v
    Kubernetes Resources
        |
        v
    Observed State
        |
        v
    Agent.status

The reconciliation process must be idempotent.

Repeated reconciliation of the same desired and observed state should not
produce unintended side effects.

## Operator Responsibilities

The initial Agent Operator is responsible for the following categories.

### Resource Watch

The Operator watches changes to resources relevant to Agent infrastructure.

Initially this includes:

- Agent resources.

Later versions may also watch:

- RuntimeClass;
- ModelPolicy;
- Capability;
- GovernancePolicy;
- other control-plane resources.

### Validation

The Operator validates that infrastructure dependencies referenced by an
Agent can be resolved.

Examples include:

- RuntimeClass exists;
- referenced configuration exists;
- required identity can be resolved;
- referenced policy resources are valid.

Validation failures should be represented through status conditions.

### Runtime Resolution

The Operator resolves the declared Agent runtime class.

For example:

    Agent
      |
      | runtimeClass = hermes
      v
    RuntimeClass/hermes
      |
      v
    Hermes Runtime Adapter

or:

    Agent
      |
      | runtimeClass = native
      v
    Native Runtime Adapter

The Operator should interact with runtime implementations through a stable
runtime adapter contract rather than embedding framework-specific lifecycle
logic directly into the core reconciliation loop.

### Infrastructure Reconciliation

The Operator creates and maintains Kubernetes resources required to run an
Agent.

The initial implementation may manage resources such as:

- Deployment;
- Service;
- ConfigMap;
- Secret references;
- ServiceAccount.

Future versions may additionally manage:

- HorizontalPodAutoscaler;
- NetworkPolicy;
- PodDisruptionBudget;
- persistent storage;
- specialized accelerator resources.

### Dependency Resolution

The Operator ensures required control-plane dependencies are available before
declaring an Agent ready.

Possible dependencies include:

- RuntimeClass;
- ModelPolicy;
- Capability;
- GovernancePolicy;
- configuration resources.

Dependency failure must not be silently ignored.

### Lifecycle Management

The Operator manages infrastructure-level Agent lifecycle including:

- creation;
- update;
- rollout;
- scaling;
- restart;
- deletion;
- failure recovery.

Lifecycle management does not include task or workflow execution.

### Status Reporting

The Operator reports observed infrastructure state through Agent.status.

Example conceptual status:

    status:
      observedGeneration: 7

      phase: Running

      readyReplicas: 3

      runtimeRef:
        name: researcher-runtime

      endpoint:
        service: researcher

      conditions:
        - type: RuntimeResolved
          status: "True"

        - type: Ready
          status: "True"

Detailed state should use Kubernetes conditions where practical.

The phase field should remain a high-level summary only.

## Reconciliation Properties

The reconciliation implementation must follow several principles.

### Idempotency

Running reconciliation multiple times for the same desired state should
produce the same stable infrastructure state.

### Level-Based Reconciliation

The Operator should primarily reconcile current desired and observed state
rather than depending on a strict sequence of historical events.

### Eventual Consistency

The control plane does not require every change to become effective
immediately.

The Operator continually converges the actual state toward desired state.

### Ownership

Resources created specifically for an Agent should normally use Kubernetes
ownership mechanisms where appropriate.

This enables Kubernetes garbage collection and simplifies lifecycle cleanup.

### Status as Observation

The Operator reports observed state.

It must not treat status as the primary source of desired configuration.

Desired state belongs in spec.

## Runtime Adapter Boundary

The core Operator should not contain implementation details for every Agent
runtime.

Instead:

    Agent Operator
          |
          v
    Runtime Adapter Interface
          |
     +----+----------------------+
     |            |              |
     v            v              v
   Native       Hermes        LangGraph
   Adapter      Adapter        Adapter

A runtime adapter may translate the common Agent resource into
runtime-specific infrastructure.

This design enables the Enterprise Agent OS to manage heterogeneous Agent
runtimes through a common control-plane contract.

The exact Runtime Adapter API will be defined in ADR-0004.

## Responsibilities Explicitly Excluded from the Operator

The Agent Operator must not become a general Agent orchestration engine.

The following responsibilities are explicitly outside the Operator:

- prompt generation;
- model reasoning;
- model inference;
- user conversation;
- session management;
- Agent memory;
- retrieval-augmented generation;
- tool execution;
- MCP execution;
- task decomposition;
- multi-Agent delegation;
- workflow orchestration;
- business process logic;
- Reviewer decisions;
- final content generation.

These concerns belong to other layers such as:

- Agent Runtime;
- Task Service;
- Workflow Engine;
- Enterprise Assistant;
- Memory services;
- Capability services;
- Model Gateway.

## Failure Handling

Infrastructure and dependency failures should be visible through status
conditions.

For example:

    conditions:
      - type: RuntimeResolved
        status: "False"
        reason: RuntimeClassNotFound

or:

    conditions:
      - type: Ready
        status: "False"
        reason: DeploymentUnavailable

The Operator should retry recoverable reconciliation failures using
controller-runtime or framework-native retry mechanisms.

Business task failures must not be represented as infrastructure
reconciliation failures.

## Alternatives Considered

### Imperative Provisioning Service

A traditional API service could receive requests and directly create
Kubernetes resources.

Rejected as the primary lifecycle model because it lacks the continuous
desired-state reconciliation semantics provided by the Operator pattern.

### Workflow Engine as Lifecycle Manager

A workflow engine could create and delete Agent infrastructure.

Rejected because workflow execution and infrastructure lifecycle have
different responsibilities and failure semantics.

Workflow engines may request changes to desired Agent state, but the Operator
remains responsible for reconciliation.

### Agent Runtime Self-Management

Each Agent Runtime could create and manage its own Kubernetes resources.

Rejected because this would duplicate infrastructure logic across runtimes
and weaken the common Enterprise Agent OS control plane.

## Consequences

### Positive

- Provides continuous desired-state reconciliation.
- Uses standard Kubernetes control-plane patterns.
- Enables self-healing infrastructure.
- Centralizes Agent lifecycle behavior.
- Separates infrastructure management from Agent reasoning.
- Supports heterogeneous Agent runtimes through adapters.
- Creates consistent status and lifecycle semantics.
- Enables future scaling, rollout, policy, and scheduling extensions.

### Negative

- Requires a reliable Operator implementation.
- Runtime adapter contracts must be carefully designed.
- Reconciliation and dependency graphs may become complex.
- Incorrect controller logic may create resource churn.
- Operators require careful status-update and retry behavior.

## Architectural Boundary

The Agent Operator answers:

    "Does the declared Agent have the infrastructure required
     to exist and remain available?"

It does not answer:

    "What task should the Agent perform?"

or:

    "Which Agent should execute the next workflow step?"

or:

    "What should the Agent reason about?"

Those questions belong to execution and orchestration layers above the
infrastructure control plane.

## Follow-up Decision

ADR-0004 defines the pluggable Agent Runtime architecture and the contract
between the Agent Operator and runtime-specific implementations.
