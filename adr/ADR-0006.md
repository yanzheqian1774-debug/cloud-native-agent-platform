# ADR-0006: Introduce a Read-Only Workflow Execution Console

- Decision Status: Accepted
- Implementation Status: Implemented
- Implementation Note: The read-only Workflow Execution Console, stateless backend projection, Kubernetes source-of-truth model, DAG/detail views, node inspection, and initial localization are implemented.
- Date: 2026-08-18
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

The platform can execute multi-Agent workflows through Kubernetes-native
Workflow and Task resources.

Operators and developers can currently inspect execution state through
Kubernetes tools such as kubectl, but the platform does not yet provide a
user-facing way to understand workflow execution.

Users need to answer questions such as:

- Which workflows have run?
- What is the current workflow phase?
- Which Agent executed each node?
- What dependencies exist between nodes?
- Which nodes executed in parallel?
- What input did a node receive?
- What result did a node produce?
- Why did a node fail?
- How many execution attempts were made?

The platform therefore requires an execution-oriented user experience without
introducing a second source of workflow state.

## Decision

The platform will introduce a Workflow Execution Console.

The Console is a read-only projection of execution state stored in Kubernetes
resources.

Conceptually:

    User
      |
      v
    Console Frontend
      |
      v
    Console Backend
      |
      v
    Kubernetes API
      |
      +-- Workflow
      +-- Task
      +-- Agent

Kubernetes resources remain the source of truth.

The Console must not become a workflow execution engine or an independent
state-management system.

## Component Boundary

The Console is distinct from the ModelGateway.

The ModelGateway is responsible for governed model inference access, provider
routing, policy enforcement, retries, failover, and model-related accounting.

The Console is responsible for presenting Agent and workflow execution state to
users.

The initial repository boundaries are:

    operator/     Kubernetes control plane
    runtime/      Agent execution runtime
    gateway/      Model Gateway
    console/      Workflow execution experience

The Console must not absorb ModelGateway responsibilities.

## Console Backend

The Console Backend provides a read-only HTTP API over execution state.

Its initial responsibilities include:

- reading Workflow resources;
- reading Task resources;
- reading Agent resources when required;
- projecting Kubernetes resources into stable API response models;
- exposing workflow run summaries;
- exposing workflow DAG topology;
- exposing node execution details.

The Console Backend must remain stateless in the initial implementation.

It must not require a database.

## Projection Model

Kubernetes resource schemas are infrastructure and control-plane contracts.

They must not be exposed directly as the long-term Console API contract.

The Console Backend therefore provides a projection layer:

    Kubernetes Resources
            |
            v
       Repository
            |
            v
       Projection
            |
            v
       API Schema
            |
            v
         Console

This allows the user-facing API to evolve independently from raw Kubernetes
resource representation while preserving Kubernetes as the source of truth.

## Read-Only Boundary

The initial Console is strictly read-only.

It must not:

- create Workflows;
- update Workflows;
- delete Workflows;
- create or modify Tasks;
- modify Agents;
- mutate execution status.

Workflow creation and editing experiences may be considered separately in
future architecture work.

## Internationalization

Machine-readable platform semantics remain language-neutral.

Examples include:

    Succeeded
    Failed
    Running
    Pending
    Skipped
    RateLimited

The Console API returns these stable machine values without translating them.

Internationalization is a presentation-layer concern.

The initial Console will support:

- en-US;
- zh-CN.

The frontend must use translation resources rather than hard-coded
user-interface strings.

English is the fallback locale.

Additional locales must be addable without changing Kubernetes resource
schemas or Console API contracts.

Agent prompts, model responses, task results, and other execution evidence are
displayed in their original form and are not automatically translated.

## Initial User Experience

The initial Console provides:

- Workflow Runs;
- Workflow Detail;
- DAG visualization;
- Node Inspector.

The Node Inspector may expose:

- Agent reference;
- execution phase;
- dependencies;
- input;
- upstream results;
- output or result;
- attempts;
- timing;
- failure reason and message.

## Deployment

Backend and frontend responsibilities are separated in source code.

The initial release does not require them to be independently deployed
microservices.

They may be packaged as one Console deployment.

## Security

The Console Backend requires read access to the Kubernetes resources necessary
to build execution projections.

Its Kubernetes permissions should follow least privilege.

The initial Console must not require write permissions to Workflow, Task, or
Agent resources.

Authentication, authorization, multi-tenancy, and enterprise identity
integration are outside the initial Console scope and require separate
architecture decisions.

## Alternatives Considered

### Reuse the Model Gateway

Rejected.

Model inference routing and workflow execution presentation are separate
architectural responsibilities.

Combining them would couple the model plane to the user-experience plane.

### Let the Browser Access the Kubernetes API Directly

Rejected.

Direct browser access would expose Kubernetes authentication, authorization,
API compatibility, and security concerns to the frontend.

The Console Backend provides a controlled projection boundary.

### Introduce a Console Database

Rejected for the initial implementation.

Workflow and Task resources already contain the execution state required for
the initial experience.

Introducing another persistent state store would create synchronization and
consistency problems without sufficient benefit.

### Translate Platform State in the Backend

Rejected.

Machine-readable API semantics should remain stable and language-neutral.

Localization belongs in the presentation layer.

## Consequences

### Positive

- Makes workflow execution understandable without requiring kubectl.
- Preserves Kubernetes as the source of truth.
- Keeps the initial Console architecture stateless.
- Separates user experience from model routing.
- Provides a stable projection boundary for future UI evolution.
- Establishes internationalization before UI strings proliferate.
- Preserves original execution evidence.

### Negative

- Introduces a new platform component.
- Requires Kubernetes read permissions for the Console Backend.
- Adds frontend build and dependency management.
- Projection schemas must be maintained as Kubernetes APIs evolve.

## Architectural Boundary

The Operator answers:

    "How should desired Agent and Workflow state converge?"

The Agent Runtime answers:

    "How should an Agent execute a Task?"

The ModelGateway answers:

    "Which allowed model should handle an inference request and how should it
     be governed?"

The Workflow Execution Console answers:

    "What happened during this workflow execution, and how can a user
     understand its current or terminal state?"

## Follow-up Work

The initial implementation will define:

- Console API contracts;
- Workflow execution projections;
- Console Backend;
- Workflow Runs;
- Workflow Detail;
- DAG visualization;
- Node Inspector;
- en-US and zh-CN localization;
- real workflow execution validation.

Future architecture work may address:

- authentication and authorization;
- multi-tenancy;
- workflow creation and editing;
- Agent management;
- logs and tracing;
- cost and token analytics;
- historical execution storage;
- enterprise observability integration.
