# ADR-0002: Model Agent as a Declarative Enterprise Resource

- Status: Accepted
- Date: 2026-08-10
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

ADR-0001 establishes Kubernetes as the infrastructure control plane for the
Enterprise Agent OS.

The platform now needs a declarative way to represent an enterprise Agent.

An Agent is more than a Kubernetes Deployment or Pod. It has higher-level
semantics including:

- identity and organizational role;
- runtime implementation;
- model policy;
- capabilities;
- infrastructure resource requirements;
- lifecycle intent;
- governance and policy associations.

The resource model must remain independent from any single Agent framework or
runtime implementation.

The platform must also avoid using the Kubernetes API server and etcd as a
database for high-frequency Agent execution state.

## Decision

An Agent will be modeled as a Kubernetes Custom Resource.

The initial conceptual API will use:

    apiVersion: agentos.example.io/v1alpha1
    kind: Agent

The exact API group may change before the first stable release.

The Agent Custom Resource represents the desired enterprise identity,
runtime configuration, capability bindings, model policy, infrastructure
requirements, lifecycle intent, and governance associations of an Agent.

The Agent resource does not contain the complete runtime execution state of
the Agent.

## Resource Model

The Agent resource follows standard Kubernetes API conventions:

    metadata
    spec
    status

### Metadata

Kubernetes metadata provides infrastructure identity and management
information including:

- name;
- namespace;
- labels;
- annotations;
- generation;
- owner references.

Enterprise organizational metadata should normally use explicit fields or
references rather than being encoded into resource names.

### Spec

`spec` represents desired state.

The initial conceptual structure is:

    spec:
      identity:
        role:
        organizationRef:

      runtimeClass:
        name:

      modelPolicyRef:

      capabilityRefs: []

      resources:
        requests:
        limits:

      lifecycle:
        replicas:

      governance:
        policyRef:
        serviceAccountRef:

This schema is intentionally small and will evolve as implementation
requirements become clearer.

## Identity

Identity describes what organizational role the Agent represents.

Examples include:

- researcher;
- architect;
- finance-analyst;
- procurement-reviewer;
- release-agent.

Identity is separate from runtime implementation.

Two Agents with the same organizational role may use different runtimes or
model policies.

## Runtime Class

The Agent must not be coupled to a single Agent framework.

`runtimeClass` identifies the runtime implementation responsible for executing
the Agent.

Conceptual examples include:

- native;
- hermes;
- langgraph;
- kagent;
- external.

The Agent Operator resolves the declared runtime class through a RuntimeClass
or adapter mechanism.

The Agent resource should not embed framework-specific runtime configuration
unless it is expressed through a dedicated referenced configuration object.

## Model Policy

The Agent should not directly encode provider credentials or hard-code all
model routing behavior.

Instead, it references a model policy.

A model policy may eventually define:

- allowed providers;
- preferred models;
- private-model-only requirements;
- data residency requirements;
- cost limits;
- fallback models;
- quality or latency policies.

This allows enterprise model governance to evolve independently from Agent
definitions.

## Capabilities

Capabilities represent reusable enterprise abilities available to an Agent.

Examples include:

- skills;
- MCP servers;
- enterprise connectors;
- controlled tools;
- knowledge services.

The Agent references capabilities rather than embedding large executable
definitions.

This enables capabilities to become independently versioned, governed,
audited, and reused enterprise assets.

## Resources

Infrastructure requirements use Kubernetes-native resource semantics where
practical.

Examples include:

- CPU;
- memory;
- GPU;
- accelerator resources.

The Agent resource expresses desired infrastructure requirements, while
Kubernetes performs scheduling and allocation.

## Lifecycle

Lifecycle fields describe infrastructure-level lifecycle intent.

The initial version may include:

- replicas;
- availability policy;
- restart-related policy.

Task-level workflow orchestration does not belong in the Agent lifecycle
section.

## Governance

The Agent may reference enterprise governance resources.

Examples include:

- policy;
- service identity;
- approval policy;
- data-access policy;
- organizational ownership.

The Agent CRD should reference these resources rather than embedding an entire
enterprise policy language directly.

## Status

`status` represents observed infrastructure state reported by controllers.

The initial conceptual structure is:

    status:
      observedGeneration:
      phase:
      conditions:
      runtimeRef:
      endpoint:
      readyReplicas:

Possible high-level phases include:

- Pending;
- Provisioning;
- Running;
- Degraded;
- Failed;
- Terminating.

Detailed machine-readable state should be represented through Kubernetes
conditions.

The phase field is only a high-level summary.

## Data That Must Not Be Stored in the Agent CRD

The Kubernetes API server and etcd must not become the primary database for
Agent execution data.

The Agent CRD must not contain large or high-frequency data including:

- conversation history;
- prompt history;
- model responses;
- token streams;
- chain-of-thought or hidden reasoning traces;
- workflow execution history;
- task event streams;
- large memory objects;
- tool outputs;
- business documents;
- inference logs;
- detailed cost events.

These belong in runtime, workflow, memory, observability, or external
persistence systems.

The Agent status subresource should contain only information necessary to
observe and reconcile Agent infrastructure lifecycle.

## Reconciliation Semantics

The Agent resource represents desired state.

Conceptually:

    Agent.spec
        |
        v
    Desired Agent State
        |
        v
    Agent Operator
        |
        | reconcile
        v
    Runtime Adapter / Deployment / Service / Configuration
        |
        v
    Observed Infrastructure State
        |
        v
    Agent.status

Users and higher-level platform components modify `spec`.

Controllers converge infrastructure toward the declared desired state.

Controllers report relevant observed state through `status`.

## Relationship to Higher-Level Resources

An Agent is intentionally not the complete representation of an enterprise
digital workforce.

Higher-level resources may later include:

- AgentTeam;
- Task;
- Workflow;
- Capability;
- ModelPolicy;
- RuntimeClass;
- GovernancePolicy.

An Enterprise Assistant may coordinate multiple Agent resources without
changing the fundamental Agent lifecycle model.

## Alternatives Considered

### Use Kubernetes Deployments Directly

Rejected because Deployments do not represent Agent-specific semantics such as
organizational identity, runtime class, model policy, capabilities, or
governance associations.

Deployments remain implementation resources managed by the control plane.

### Use ConfigMaps as Agent Definitions

Rejected because ConfigMaps do not provide a strongly typed API contract,
status subresource, lifecycle semantics, or reconciliation contract.

### Store Agent Definitions Only in an External Database

Rejected as the sole source of truth for Kubernetes-managed Agent lifecycle
because it would create a second infrastructure desired-state system outside
the Kubernetes control plane.

An external database may still store product metadata that does not belong in
the Kubernetes resource model.

### Couple the Agent Resource to a Single Runtime

Rejected because this would turn the platform into another Agent framework
rather than an open enterprise Agent control plane.

## Consequences

### Positive

- Establishes Agent as a first-class declarative enterprise resource.
- Preserves Kubernetes-native lifecycle management.
- Decouples Agent identity from runtime implementation.
- Enables multiple Agent frameworks and runtimes.
- Enables model governance through policy references.
- Enables reusable capability assets.
- Creates a clean foundation for enterprise governance.
- Provides a stable contract for the Agent Operator.

### Negative

- Requires careful API versioning and compatibility management.
- Requires additional resources such as RuntimeClass and ModelPolicy.
- Introduces more indirection than embedding everything in one YAML file.
- Poorly designed references could create complex dependency management.
- Operators must avoid excessive status updates.

## Architectural Boundary

The Agent CRD answers:

    "What enterprise Agent should exist, what role does it represent,
     which runtime class should execute it, which model policy and
     capabilities should it use, and under what governance constraints?"

It does not answer:

    "What is this Agent currently thinking about?"

or:

    "What business task is this Agent currently executing?"

Those concerns belong to Task, Workflow, Session, Runtime, Memory, and
Observability layers.
