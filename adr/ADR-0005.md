# ADR-0005: Introduce Model Provider, Model Policy, and Model Gateway Abstractions

- Decision Status: Accepted
- Implementation Status: Partial
- Implementation Note: Partial implementation with known architecture drift. The runtime contains a runtime-local ModelProvider interface with mock and OpenAI-compatible implementations. This is not the platform-level ModelProvider/ModelPolicy/ModelGateway architecture defined by this ADR. Current Agent configuration embeds model provider/name information and passes it toward the runtime instead of referencing ModelPolicy and routing through ModelGateway.
- Date: 2026-08-10
- Decision Owners: Cloud Native Agent Platform Contributors

## Context

ADR-0002 defines Agent as a declarative enterprise resource.

ADR-0004 defines a pluggable Agent Runtime architecture.

Different Agent runtimes may use different model providers, model APIs, and
model-selection mechanisms.

Directly binding each Agent to a specific model provider and model identifier
would create several enterprise problems:

- provider lock-in;
- limited failover capability;
- duplicated authentication configuration;
- inconsistent cost controls;
- inconsistent data-governance enforcement;
- inability to route workloads based on latency, quality, or capability;
- difficulty migrating Agents between model providers.

The Enterprise Agent OS therefore requires a model abstraction that separates
Agent intent from provider-specific execution.

## Decision

The platform will introduce three model-layer abstractions:

- ModelProvider;
- ModelPolicy;
- ModelGateway.

Agents reference a ModelPolicy rather than directly owning complete
provider-specific model configuration.

The ModelGateway evaluates policy, selects an appropriate provider and model,
and routes inference requests through provider adapters.

## ModelProvider

A ModelProvider represents a reusable provider integration.

Conceptual examples include:

- Qwen;
- Kimi;
- OpenAI;
- Claude;
- DeepSeek;
- vLLM;
- Ollama;
- enterprise private model services.

A ModelProvider may define or reference:

- provider type;
- endpoint configuration;
- authentication configuration;
- supported capabilities;
- region;
- health status;
- provider metadata.

Sensitive credentials must not be stored directly in Agent resources.

Credentials should be referenced through Kubernetes Secrets or an external
secret-management system.

## ModelPolicy

A ModelPolicy represents enterprise intent for model selection and use.

An Agent references a ModelPolicy.

A policy may eventually express requirements such as:

- required capabilities;
- preferred providers;
- preferred models;
- fallback order;
- cost constraints;
- latency constraints;
- data classification restrictions;
- geographic or residency restrictions;
- private-model-only requirements;
- context-length requirements;
- availability requirements.

The exact schema will be defined during implementation.

Conceptually:

    Agent
      |
      | modelPolicyRef
      v
    research-model-policy
      |
      +-- capability: reasoning
      +-- capability: long-context
      +-- strategy: quality-first
      +-- preferred providers
      +-- fallback rules
      +-- governance constraints

## ModelGateway

The ModelGateway provides a common enterprise access layer for model
inference.

Its responsibilities may include:

- provider routing;
- authentication;
- rate limiting;
- retries;
- failover;
- model fallback;
- policy enforcement;
- token accounting;
- cost accounting;
- audit events;
- health checking;
- request metadata propagation.

The ModelGateway is not responsible for Agent reasoning or workflow
orchestration.

## Provider Adapter Contract

Provider-specific APIs are hidden behind provider adapters.

The initial conceptual provider contract includes:

    complete(request)

    stream(request)

    health()

Future versions may add capabilities such as:

    embed(request)

    tokenize(request)

    capabilities()

The initial implementation should remain minimal.

## Routing

The ModelGateway may support multiple routing strategies.

Potential strategies include:

- quality-first;
- cost-first;
- latency-first;
- private-first;
- capability-based;
- region-restricted;
- weighted load balancing;
- failover.

Routing decisions must respect governance constraints before optimization
criteria.

For example:

    Data classification = Secret
        |
        v
    Policy evaluation
        |
        v
    External provider prohibited
        |
        v
    Private model selected

Cost or latency optimization must never override mandatory security or data
governance requirements.

## Capability-Based Selection

Different models may expose different capabilities.

Examples include:

- long context;
- reasoning;
- coding;
- multimodal input;
- tool calling;
- structured output;
- embeddings.

The routing layer may use capability metadata when matching an Agent or task
to a model.

The platform must not assume that every provider exposes identical features.

## Runtime Independence

Agent runtimes may interact with models through different internal APIs.

The Enterprise Agent OS should encourage use of the common ModelGateway where
enterprise governance is required.

However, the platform must support heterogeneous runtimes.

A runtime that uses its own model client may still be integrated, but its
model access may have reduced governance visibility unless routed through an
approved gateway or adapter.

This limitation should be observable and governable.

## Security and Data Governance

Model routing crosses an enterprise data boundary.

The model layer must eventually support policy evaluation based on information
such as:

- user identity;
- Agent identity;
- tenant;
- business unit;
- task context;
- data classification;
- provider location;
- model trust level.

External model access must not automatically receive enterprise-sensitive
data.

## Cost Governance

The ModelGateway should provide consistent usage accounting.

The platform should eventually record:

- input tokens;
- output tokens;
- request count;
- latency;
- provider;
- selected model;
- estimated cost;
- Agent;
- task;
- tenant or business unit.

Cost events should be stored in an observability or billing system rather than
inside Agent CRD status.

## Failure Handling

Provider failures should be classified separately from Agent lifecycle
failures.

Examples include:

- provider unavailable;
- model unavailable;
- rate limit exceeded;
- timeout;
- invalid credentials;
- policy denied.

Model fallback may be used where allowed by policy.

Fallback decisions should be auditable.

## Alternatives Considered

### Hard-Code Model Configuration in Agent

Rejected because it tightly couples Agent definitions to provider-specific
configuration and weakens enterprise routing and governance.

### Let Each Runtime Manage Providers Independently

Rejected as the default enterprise architecture because it fragments
authentication, observability, cost management, and governance.

Runtimes may still maintain internal provider logic where necessary, but the
platform should provide a common governed path.

### Use Only One Enterprise Model Provider

Rejected because model capability, price, latency, availability, regulation,
and enterprise requirements change over time.

The platform should preserve provider portability.

### Require a Single OpenAI-Compatible Protocol Everywhere

Rejected as the sole internal abstraction.

OpenAI-compatible APIs are useful for interoperability, but not every provider
or capability maps perfectly to a single protocol.

Provider adapters allow the platform to normalize common operations while
retaining provider-specific capability metadata.

## Consequences

### Positive

- Decouples Agent definitions from individual model vendors.
- Supports provider migration and failover.
- Centralizes enterprise model governance.
- Enables cost and usage accounting.
- Enables capability-aware routing.
- Enables private/public model combinations.
- Provides consistent observability across model providers.
- Reduces provider-specific logic inside Agent runtimes.

### Negative

- Adds a model routing layer and operational complexity.
- Provider capabilities must be normalized carefully.
- Streaming and tool-calling differences may complicate adapters.
- Gateway outages may affect multiple Agent runtimes.
- Runtime bypass of the gateway can reduce governance visibility.

## Architectural Boundary

The ModelPolicy answers:

    "What model characteristics and governance constraints should apply
     to this Agent or task?"

The ModelGateway answers:

    "Which allowed model should handle this request and how should that
     request be routed, observed, and accounted for?"

The Agent Runtime answers:

    "How should the selected model be used as part of Agent execution?"

## Strategic Consequence

The Enterprise Agent OS treats model providers as interchangeable execution
resources governed by enterprise policy.

The competitive value of the platform does not depend on owning the best
foundation model.

Instead, the platform enables enterprises to safely and economically use
multiple current and future models as part of one governed digital workforce.

## Follow-up Architecture Work

Future architecture decisions will define:

- Task and execution model;
- AgentTeam and workflow model;
- enterprise capability registry;
- identity and governance model;
- session, memory, and knowledge architecture;
- observability, evaluation, audit, and cost architecture.
